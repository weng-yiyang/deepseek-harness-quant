# 更新与发布机制

本仓库自带**增量覆盖更新机制**：主系统的任何改动可打包成更新包（zip），应用到开源项目而不破坏用户配置与数据。

## 一、版本

- `VERSION` 文件记录当前版本（semver：主.次.修订）
- `CHANGELOG.md` 记录每个版本变更

## 二、生成更新包（开发者/维护者侧）

在主系统机器上运行：

```bash
python <开源根>/scripts/build_update.py --from <主系统根目录> --version 1.0.4
# 产物: <开源根>/updates/update_1.0.4.zip
```

机制：

- 对比 主系统白名单文件（脱敏后） vs 开源包同路径 → 差异 = files；主系统已删除的 → removed
- **自动脱敏**：D:/数据目录、C:\Users\&lt;用户名&gt;、私有服务器域名、token 模式 全部替换为开源相对路径/占位——更新包永不携带主系统私有信息
- 白名单外路径（node_modules/用户配置/数据）永不进入更新包

## 三、应用更新（用户侧）

```bash
python scripts/update.py update_1.0.4.zip        # 直接应用
python scripts/update.py update_1.0.4.zip --dry-run   # 先预览
```

机制：

1. 校验 manifest（版本/文件清单）与**白名单**——任何越界路径直接拒绝
2. **自动备份**被覆盖文件 → `backups/<时间戳>/`（可手动回滚）
3. 覆盖 files / 删除 removed（仅白名单内）
4. 更新 VERSION

## 四、保护清单（永不覆盖/永不删除）

| 类别 | 内容 |
|---|---|
| 用户配置 | `config/params.yaml`、`config/strategies.yaml`、`config/etf_pool.yaml` |
| HARNESS 凭据 | `harness/home/.credentials.yaml` |
| 用户数据 | `harness/home/sessions/`、`harness/home/storages/`、`data/cache/`、`data/factorpool/`、`data/demo/`、`logs/`、`output/` |
| 数据库文件 | 所有 `*.db` / `*.parquet` |
| 运行时 | `harness/node_modules/`（如需升级运行时请重跑 `harness/install.cmd`） |
| 开源包特有 | `LICENSE`、`CHANGELOG.md`、`AGENTS.md`、`docs/`、`config/*.example`、`scripts/`（工具自身）、`deck/__init__.py` |

## 五、回滚

应用后如发现问题：

```bash
# 1. 查看最近备份
ls backups/
# 2. 手动恢复（示例）
copy backups\20260816_101530\files\backtest\bt_runner.py backtest\bt_runner.py
```

## 六、发布流程建议

1. 主系统改动完成 + 回归验证
2. `build_update.py` 生成更新包（版本号递增）
3. 检查 `updates/update_<ver>.zip` 的 manifest（files/removed 合理）
4. 发布：GitHub Release 附件 + CHANGELOG 更新
5. 用户：下载 zip → `python scripts/update.py update_<ver>.zip`

## 七、维护注意

- `scripts/build_update.py` 与 `scripts/update.py` 的白名单/保护清单**必须保持一致**（同一套规则，改一侧同步另一侧）
- 更新包体积 = 变更文件大小；若 files 数量异常大，先检查是否主系统新增了不该进开源包的文件
- 脱敏规则在 `build_update.py` 的 `_SAN_PATS`——新增私有路径标识时同步补充
